## 1. 选题背景与创新点

**要解决的问题**：产线上的视觉检测（计数、液位、缺件）通常有两种做法。用 PC + 显卡，成本高、功耗大、要联网，现场布线困难；用纯 FPGA 做固定网络，一旦换产品、换模型就要重新综合比特流，迭代周期以天计。小批量多品种的产线恰恰换型最频繁。

**本作品的取舍**：把「网络结构」和「网络参数」分开。PL 实现的是一套固定的算子图（33 条命令、21 层卷积），换模型时只下发参数包与算子图，**不重新综合比特流**；PS 负责把算子逐条喂给 PL，并处理所有控制密集、规则频繁变化的部分（预处理、解码、跟踪、判定、显示排版）。

**创新点**

1. **双 INT8 乘法打包**：一个 DSP 乘法同时算出两个 INT8 乘积（配合高半部符号修正），使 220 DSP 的资源上限下，48×8 的并行阵列能用 192 个 DSP 承载 384 路乘法。这是本项目能在该器件上跑完整网络的前提，而不是可选项。
2. **行装载与计算重叠**：卷积的输入行补齐/权重重排与计算流水并行，输入、权重、部分和各自双缓冲，减少纯搬运时间。
3. **模型换型不重综合**：33 条命令的固定图 + 参数包（含 CRC/SHA/版本/图匹配校验）构成可换型的运行时，交付的 bitstream 一个版本覆盖多种产品。
4. **端到端闭环**：同一块板完成采集、推理、判定、本地 HDMI 显示和网络回传；平台侧有批次、证据留存与人工复核，检测结果可追溯，不是一次性的演示。

## 2. 设计原理与功能框图

```
OV5640 ──(DVP)──> PL 采集(416×416 RGB565, 异步 FIFO) ──(AXI DMA S2MM)──> DDR
                                                                          │
      ┌───────────────────────────────────────────────────────────────────┘
      ▼
  ARM Cortex-A9：灰度/颜色校正 → 逐条下发 33 条命令 → 解码 → 跟踪 → 规则判定
      │                                                    ▲
      │ 8 个 AXI master bundle（FM1~4 / W1~4，共享 4 个 HP 口）
      ▼                                                    │
  PL：48×8 INT8 卷积阵列（192 DSP，125 MHz） ──────────────┘
      │
      └──> PS 组帧 RGB565 framebuffer ──> PL 扫描输出 720p25 HDMI
```

**数值精度**：W8A8——权重与激活 INT8，部分和 INT32，重定标用 INT64 后舍入饱和回 INT8；负半轴由参数实现，避免额外激活函数开销。PS 侧整数参考实现与 PL 必须**逐字节一致**，这是功能正确性的判据。

**并行结构**：`Tm=48`、`Tn=8` 的乘加阵列；8 个 master bundle 分组复用 4 个 HP 口访问共享 DDR，因此采集、显示、推理会争用带宽——这一约束直接决定了后续优化的方向（减少搬运，而不是一味提高频率）。

**显示**：PS 绘制 RGB565 帧缓冲，PL 扫描到 720p，像素时钟约 30.94 MHz、TMDS 串行时钟约 154.69 MHz，面板 25 Hz 更新。

## 3. 软硬件划分依据与接口设计

划分不是按「哪边快」，而是按「谁更不容易变」：

| 功能 | 放在 | 理由 |
|---|---|---|
| 卷积/池化/上采样 | PL | 规则、可并行、算力需求大；一次综合长期复用 |
| 灰度与色彩校正 | PS | 参数随产品变（不同颜色/光照），改一次不用重综合 |
| 算子调度 | PS | 换模型只换命令序列；PL 只认「一条命令一次启动」 |
| 解码、跟踪、判定 | PS | 规则与阈值频繁调整，且需要浮点/查表 |
| 采集与显示扫描 | PL | 硬实时、与 CPU 负载解耦 |

**接口**

- 采集：DVP → 异步 FIFO → AXI DMA S2MM → DDR（416×416 RGB565，32 位打包）。
- 计算：寄存器命令接口，每条命令一次启动；权重/输入/输出各走独立 AXI master，分组共享 4 个 HP。
- 显示：PS 写 framebuffer，PL 读并扫描输出（1280×720，16 bpp，双页防撕裂）。
- 远程：PS 侧 HTTP 预览与批次/模型接口；裸机路径另保留 UDP 输出到上位机。

## 4. 优化过程

不同版本的基线不同，下表按时间排列，**数字之间不可连成一条曲线**：

| 优化 | 效果 | 证据 |
|---|---|---|
| 行读取/解包与计算重叠 | 卷积 56.916 → 54.247 ms（−4.689%） | 见 `docs/cnn-accelerator-performance.md` 与 2026-10-26 部署记录 |
| 收敛后的固定输入复算 | 21 层卷积 52.544 ms；33 命令 57.607 ms | 2026-10-27 两轮固定输入 CSV 离线复算 |
| 端到端（RGB + 显示） | 15.21 FPS（121.527 s 连续运行） | `docs/competition/02_EVIDENCE_INDEX.md` E23 |
| 失败的尝试（保留记录） | 组合输入缓存因拥塞停止；BRAM FIFO 多占 16 个 BRAM18K 未采用；某版 127.9 → 133.7 ms 回退 | E32 |

**判断依据**（不是试出来的）：

- 资源账：DSP 217/220，已无空间再扩阵列；LUT 85%，时序 WNS 仅 +0.045 ns，没有余量做大改。
- 带宽账：8 个 master 共享 4 个 HP，采集与显示会抢占推理带宽，所以优化优先减少重复搬运（行重叠、缓存、双缓冲），而不是提高时钟。
- 因此后续优化集中在「同样的数据搬一次干更多的活」，以及把控制开销（命令交接）压到最低。

## 7. 复现说明

完整步骤见 [README 第 5 节](../README.md#5-复现步骤)，关键节点：

1. 环境：Windows + Vivado/Vitis 2026.1；`AMD_TOOLS_ROOT` 可覆盖默认安装路径。
2. `hardware/hls/build.ps1` 生成 CNN IP（目标 7 ns，`xc7z020clg400-2`）。
3. `hardware/camera/build.ps1` 生成 `system_wrapper.bit` 与实现报告。
4. `camera/terminal/build.ps1` + `build-boot.ps1` 生成板端 Linux 终端与启动镜像。
5. 上板后以「整网 INT8 逐字节一致」作为功能判据，再记录帧率与耗时。

**复现判据**：给定同一输入与权重，PS 参考实现与 PL 输出必须逐字节相同；资源与时序应能复现到 [build/report/](../build/report/) 同量级（LUT ±5%、WNS 同号）。

## 8. 已知缺口

主动列出，避免夸大：

1. **无 RTL/HLS 级 testbench**：HLS 脚本只有 `csynth` + `export`，没有 csim/cosim；功能正确性靠板级整网整数对拍。
2. **协作记录不完整**：只有一轮示例对话（第 5 节）。
3. **板卡实时状态未复核**：文中性能数字均为历史实测，条件已在 README 表格注明；本次整理未上板。
4. **部分旧证据缺失**：早期版本的原始 JSON/日志未全部保留，相关结论在证据索引里已标注可信度。
5. **未提供 PYNQ Skill**：作品是自研运行时而非 PYNQ overlay，故不申请该项加分。
