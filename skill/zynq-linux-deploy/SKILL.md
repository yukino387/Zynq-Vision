# Zynq Linux 部署与恢复工作流

适用：已有 Linux 服务的板端程序更新、启动设置和显示 UI 修复。迁移到其他 Linux 嵌入式设备时替换连接、服务管理、存储和启动机制。这里提供工作流和记录模板，不含会操作设备的通用刷机脚本。

## 使用方法

复制 [deployment.md](deployment.md) 填写设备契约，再把 [prompt.md](prompt.md) 的提示词与契约交给助手或按表人工执行。只有当前任务包含部署时才操作设备；仅复核不执行命令。

1. 重新查询启动方式、网络/串口、进程、模型/产品/批次、生产或演示模式。将需恢复的状态写入记录。旧会话不能证明现场状态。
2. 软件更新只构建受影响目标；记录候选哈希，备份将替换的文件。保留无关修改，不因修 UI 重跑硬件构建。
3. 在 RAM 试运行单一候选实例。检查输出、错误和受影响功能；UI 包含提前进页面、异步状态到达、切换、退出重进和进程重启。
4. 写正式介质前检查内核 I/O 错误及有界写入/fsync/读回。异常时停止写盘并保存证据，转 RAM/离线检查；不靠反复覆盖“试好”。
5. 安装后核对候选、板端文件、交付文件哈希；按用户目标保留新状态，恢复试验额外改变的服务和调频设置。
6. 分别记录 RAM、持久文件安装、进程重启、软件复位、断电冷启动。没做的标未验证。

Zynq-7000 Linux 中还需依据当前驱动/工程约定检查 SLCR；本队经验是 Linux 运行保持解锁。其他 SoC 不套用地址或解锁命令。解锁不证明 SD 写入可靠；JTAG 下载不证明 QSPI/SD 持久启动。

## 失效条件与效果

没有可恢复备份、启动链未知或存储读回失败时不继续正式写入。失联先区分地址、接口和服务，不循环要求断电。服务默认页面与状态机不同于本案例时需要新测，不直接复制面板逻辑。

历史效果、真实交互摘录和限制见 [case.md](case.md) 与 [evidence/deploy_result.json](../evidence/deploy_result.json)。本次仅整理离线材料，没有部署或冷启动复测。
