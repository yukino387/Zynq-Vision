彩色模型交付标准

给训练侧队友的交付口径：按这份标准产出 model.bin，平台导入、板端下发和 PS 端色彩模式识别都不需要再改代码。

版本 v1.0 日期 2026-10-17 适用固件 2026-10-17 16:13 及以后 适用平台 CNN Studio / vision server

三句话版本

  1. 用项目固定图训练，colorMode=RGB，输入 224×224×3；不要改网络、锚点、输出尺度。
  2. 交付 model.bin（6,416,360 字节）+ 六槽类别表 + 验证报告；类别名不写进模型包。
  3. 板端只要读到 metadata[4]=3 就自动走 RGB 预处理；metadata[4]=1 的灰度模型继续可用。

01 · 链路现状PS 端已经打通的部分

板端加载路径是：模型包写入 SD 槽位 → model_store.cpp 校验并加载 weights/metadata → live_main.cpp 读 metadata[4] → gray.cpp 选灰度或 RGB 预处理 → 写入 features 的 1 或 3 个平面 → PL 固定图推理。

metadata[4] 就是第一层卷积的输入通道数（commands[0][4]）。它是模型包自带的，不是固件配置、不需要 manifest、也不需要上位机告诉板子。平台导入时，服务器同样从 model.bin 的 metadata 读出通道数，自动生成 preprocessProfile。

固件前提：板上必须是 2026-10-17 16:13 之后构建的 ELF（含 model_store 与通道自动识别）。更早的固件没有这套模型库与彩色分支，彩色包能下发但不会按 RGB 预处理。当前板上若仍是旧固件，先用 vitis_live/run_live.tcl 加载最新 ELF，再验收彩色模型。QSPI 自启动镜像需另行重建，现有 BOOT.bin 早于该 ELF。

03 · 预处理彩色输入必须和板端逐位对齐

相机给的是 416×416 RGB565；PS 先解出 R/G/B 8-bit，再用 camera/int8/gray_coefficients.h 的定点系数做两遍 resize 到 224×224，最后量化成 INT8。

环节彩色（RGB）灰度（GRAY）
训练参数colorMode = "RGB"colorMode = "GRAY"
metadata[4]31
manifest 预处理标识RGB565_RGB224_INT8_V1RGB565_GRAY224_INT8_V1
通道顺序RGB，不是 BGR亮度 luma
输入尺寸224×224224×224
量化x_int8 = (clip(x, 0, 255) × 127 + 127) // 255；网络输入 x_int8 / 127；zero point 0，scale 1/127

必须使用项目自带的数据预处理：camera/training/data.py 的 Samples(..., "RGB") 会先按 BICUBIC 缩到 416，再模拟 RGB565 量化，最后用与 PS 相同的定点表做两遍 resize。不要自己写 resize、不要做 mean/std、不要转 HSV/YUV、不要用 416 或 320 的输入尺寸。

如果样本是原始采集文件（raw），必须是 416×416、little-endian RGB565，长度恰好 416×416×2 字节。

04 · 包格式model.bin 的字节布局

偏移长度内容
04magic 0x314e4e43
44format = 1
84weight_size = 6,350,208
124metadata_size = 66,024
164generation = 0
204committed = 0
2464version：1–63 个 ASCII 字节，NUL 补齐

1204header 前 120 字节的 CRC32
1244reserved = 0
1286,350,208weights
6,350,33666,024metadata
6,416,360—文件总长

metadata 的前 330 个 int32 是 33×10 的 commands 表；commands[0][4] 就是通道数。其余是逐层量化表，由导出链生成，不要手改。权重按 [M/48, N/8, 4, 12, 8, K, K] 打包，通道轴零补齐。

两个哈希不要混：manifest.weights.sha256 是整个 model.bin 的 SHA-256；包头 88–119 字节是 payload（weights + metadata）的 SHA-256。包内 CRC32 只覆盖包头前 120 字节。

05 · 训练与导出用项目链路，不要手工拼包

推荐直接走平台训练任务：创建训练时把颜色模式设为 RGB，训练完成后导出目录里会同时得到 model.bin、weights.bin、metadata.bin、manifest.json、checkpoint.pt 和 report.json。

命令行训练时，spec 至少要包含：

{
  "version": "MILK-RGB-20261017",
  "datasetChecksum": "<冻结数据集校验值>",
  "options": { "colorMode": "RGB", "epochs": 50, "batchSize": 32, "seed": 7020 },
  "classes": ["次品", "_unused_1", "_unused_2", "_unused_3", "_unused_4", "_unused_5"],
  "items": [ ... 冻结样本 ... ]
}

运行：

python camera/training/train.py --spec <spec.json> --output <输出目录>

如果要从已有 weights.bin/metadata.bin 重新打包，使用：

python camera/pack_model.py --weights <weights.bin> --metadata <metadata.bin> \
  --channels 3 --version <VERSION> --output <输出目录>
不要把灰度训练的权重直接加 --channels 3：包会通过校验、板子也会按 RGB 跑，但第一层只读到 R 通道，结果是错的。--channels 必须与训练时的 colorMode 一致。

版本号要求：1–63 个 ASCII 字节、不含 NUL、全局唯一；建议 产品-COLOR-日期，例如 MILK-RGB-20261017。

06 · 交付物队友需要交哪些文件

模型制品

model.bin，必须恰好 6,416,360 字节；附整包 SHA-256。

清单与类别

manifest.json（自动生成）+ 六槽类别表，按 classId 顺序列出；不足的槽写 _unused_N。

训练报告

report.json、checkpoint.pt、训练参数、数据集 ID/校验值、colorMode。

验证证据

验证集原图 + 预测结果；推荐阈值和对应分数；最差样本与已知限制（背景、光照、场景）。

所有文件放在一个目录或压缩包里交接，目录名建议 color_model_<产品>_<日期>/，并附一页 README 写明版本、类别表、阈值、哈希和训练参数。不要直接改仓库源码或板端固件。

07 · 验收交付前按顺序跑完

  1. 文件完整性。用下面的脚本检查尺寸、magic、尺寸字段、CRC、payload 哈希和通道数；输出应为 ok 3 6416360。
  2. 固定图校验。pack_model.py 或 export_int8 不应报 PL command template mismatch / PL shift 错误。
  3. 平台导入。模型仓库 → 导入模型制品，填写名称和六槽类别。预期提示“制品校验通过”；在模型详情的“技术详情”里，manifest.input.channels 为 3、preprocessProfile 为 RGB565_RGB224_INT8_V1。
  4. 板端下发。先完成评估，再由管理员批准并创建部署。预期回执 downloaded / verified / loaded / selfTest / active 全为 true，板端不报校验错误。
  5. 确认自动识别。模型激活后，板端 metadata[4] 应为 3；同一场景下彩色模型与灰度模型的 conversion_us 会不同，且推理帧的 errorCode 为 0。
  6. 整数路径对齐。用 pl_model.py 的 integer_forward 对同一张预处理后的输入算一遍，与板端输出比较类别和分数；分数应在约定容差内。
  7. 性能与稳定性。记录 conversion_us、inference_us、cycle_us 和 FPS，连续跑一段短测。彩色预处理目前是标量实现，首次上板务必记录真实数据，不要用灰度的数字代替。
  8. 回归。切回一个灰度模型（metadata[4]=1），确认仍能正常加载和推理。
import hashlib, struct, zlib
p = open('model.bin', 'rb').read()
assert len(p) == 6416360, len(p)
magic, fmt, w, m = struct.unpack('<4I', p[:16])
assert (magic, fmt, w, m) == (0x314e4e43, 1, 6350208, 66024)
assert p[124:128] == b'\0' * 4
assert zlib.crc32(p[:120]) & 0xffffffff == struct.unpack('<I', p[120:124])[0]
payload = p[128:]
assert hashlib.sha256(payload).digest() == p[88:120]
channels = struct.unpack('<i', p[128 + 6350208 + 16:128 + 6350208 + 20])[0]
assert channels in (1, 3)
print('ok', channels, len(p))

08 · 业务接入类别、阈值和显示

模型包只带权重和量化表，不带类别名。六槽类别按 classId 顺序与平台标签表对齐；平台当前在 packages/device-protocol/src/postprocess.ts 里有一张固定的六类标签表，新业务上线时要同步更新这张表和导入时填写的类别。

  • 单类别业务（例如牛奶次品）：把目标类放第 0 槽，其余五槽填 _unused_N；后处理取分数最高的槽，未使用槽的分数必须足够低。
  • 阈值不写进模型。检测阈值是平台业务参数（当前 detect() 默认 0.35）；队友在验证报告里给出推荐阈值和对应分数，由平台侧配置。
  • 输出尺度和锚点是固定常量，不随训练变化；不要为了让分数好看去改它们。
  • 如果演示使用 CNN Studio 上位机，它的 anchors/类别表也要同步；服务端和上位机是两套后处理，不能只改一边。
无缝接入的判断标准：平台导入不报错、下发自检通过、板端按 RGB 预处理、同一场景下检测结果与训练侧整数参考一致、类别名和阈值符合业务约定。

09 · 禁止事项这些改动会直接让包失效

  • 改 graph.json、commands、feature 偏移、锚点或输出尺度。
  • 改输入尺寸（416、320、256 都不行）、通道顺序（BGR）或归一化方式（mean/std）。
  • 手改 weights.bin、metadata.bin 或 model.bin 的头部字段。
  • 用 1/3 以外的通道数；用 --channels 3 去包装灰度权重。
  • 只交 checkpoint.pt 或训练日志，不交 model.bin。
  • 把“评估通过”当作“发布批准”；发布仍需管理员批准。

10 · 交接前最后一遍检查清单

  • model.bin 是 6,416,360 字节，CRC、payload SHA-256 和整包 SHA-256 都通过。
  • 包内 metadata[4] = 3，训练确实是 colorMode=RGB。
  • 六槽类别表齐全，顺序与平台标签表一致；未使用槽为 _unused_N。
  • report.json 含验证指标、推荐阈值、数据集校验值和 colorMode。
  • 平台导入、评估、批准、下发自检全部通过，且记录了三项耗时和 FPS。
  • 已用同一场景对比彩色与灰度模型，确认 RGB 路径生效、结果符合预期。
  • 交付目录附 README：版本、日期、类别、阈值、哈希、已知限制。
  • 验收板已加载 2026-10-17 16:13 及以后的 ELF；若用 QSPI 自启动，BOOT.bin 已重建并烧写。
这份标准对应当前固定图与 PS 固件行为。固件、图结构、输出尺度或后处理一旦变化，需要同步更新本页再交付。
